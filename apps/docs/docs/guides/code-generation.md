# Code generation

A contract written in TypeScript needs no build step. When the description comes from elsewhere (an OpenAPI document,
a NestJS or Express application), Polycanal **generates** a readable TypeScript contract with runtime schemas (Zod by
default), which the front end imports like a handwritten one.

A handwritten contract imports no server code, so the back end and the front end both import the same file from a
[shared package or directory](../concepts/architecture.md#shared-contract): a workspace package in a monorepo, or a
package published to a (private) npm registry when they live in separate repositories.

## From OpenAPI

```bash
npm install --save-dev @polycanal/openapi
npx polycanal-openapi openapi.json src/contract.generated.ts --export api
```

Or programmatically:

```ts
import { generateFromOpenApi } from '@polycanal/openapi';

const { source, warnings } = generateFromOpenApi(document, { exportName: 'api' });
```

OpenAPI 3.0 and 3.1 documents in JSON are supported (parse YAML first if needed).

- **Names:** `[first tag, operationId]` in camelCase (`pets.listPets`); without `operationId`, the name is built from
  the method and the path (`pets.deletePetsByPetId`). Pass `naming` to change it.
- **Parameters:** path, query and header parameters become fields with their source; names that are not identifiers
  are camel-cased and aliased (`X-Tenant` → `xTenant`).
- **Bodies:** an object JSON body is spread into `body` fields; any other body becomes a root `body` field.
- **File uploads:** without JSON content, an object `multipart/form-data` body is spread into `body` fields and the
  binding gets `body: 'multipart'`. `format: binary` properties become `z.file()`, constrained by the
  `encoding.<field>.contentType` media types (wildcards such as `image/*` are left out).
- **Responses:** the first 2xx JSON response is the output (no content: `z.void()`); 4xx and 5xx JSON responses
  become `errors`. A 2xx binary response (`format: binary` schema, or `application/octet-stream`, `image/*`,
  `application/pdf`... without schema) gives `response: 'blob'` and a `z.file()` output.
- **Schemas:** `components.schemas` become exported constants (`PetSchema`), recursive ones through `z.lazy()`.
- **Skipped, with a warning:** `HEAD`, `OPTIONS` and `TRACE` operations, cookie parameters, request bodies that are
  neither JSON nor multipart, multipart bodies that are not objects or that belong to a `GET` / `DELETE` operation,
  path parameters that are not identifiers.

## Generated code

```ts
// Generated by Polycanal. Do not edit: regenerate instead.

import { action, defineContract, input } from '@polycanal/core';
import { rest } from '@polycanal/rest';
import { z } from 'zod';

export const PetSchema = z.object({
  id: z.string(),
  name: z.string(),
  parent: z.lazy(() => PetSchema).optional(),
});

export const api = defineContract({
  pets: {
    getPet: action({
      transport: rest.get('/pets/:petId'),
      input: input({
        petId: { source: 'path', schema: z.string() },
      }),
      output: PetSchema,
    }),
  },
});
```

## Programmatic API

`@polycanal/codegen` is the layer the importers and the server adapters build on:

- `ContractDescription`: serializable form of a contract (operations with JSON Schemas, named schemas referenced as
  `#/schemas/<name>`);
- `describeContract(contract)`: description of a contract written in TS (input side of the schemas for what is sent,
  output side for what is received);
- `mergeDescriptions(config, discovered)`: config operations always win; disagreements are reported;
- `generateContractSource(description, { validation, bindings })`: TypeScript source, with a validation driver
  (`zodDriver` from `@polycanal/zod`) and binding emitters (`restBindingEmitter` from `@polycanal/rest`).
